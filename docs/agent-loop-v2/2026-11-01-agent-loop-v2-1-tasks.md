# agent-loop v2.1 speed: ordered task list (draft 1)

Date: 2026-11-01. Source: Edan, asking for a much faster loop; evidence in the speed research (not published: measured CI breakdown, wave 6 timings, ranked ideas).

Execution model: as v2. Waves; tasks in a wave run in parallel; each wave ends with a tail task that runs alone. A choice inside the **decision envelope** below is made by the loop, not by a human.

## End goal

A wave of small tasks finishes in the time of its slowest task plus one CI run plus one default-branch CI wait per merged task (merges are serialized and each is verified before the next), not in the sum of every wait. Concretely: no FIX round caused by pending CI; no model reasoning in the merge (one low-cost relay agent runs one command and returns its JSON; the script exists for speed and determinism only). Whether that command runs unattended is governed by Edan's own permission settings; if the permission system blocks it, the script does not run, the workflow stops and reports the block, and nothing retries another way; no full local check duplicated by CI; small low-risk tasks skip the critic; and every wave's scorecard shows minutes per phase so the next speedup is chosen from numbers. Target: a 4-task wave that took 34 + 51 min in wave 6 runs in under 40 min total, with the same MERGE-only-on-green-CI guarantee.

## Invariants (v2 rules stay)

1. Never commit to main, never force push; hookify rules not weakened. Merges happen only through a PR, only when CI is green on the PR head.
2. Deterministic control flow decides what runs next; models decide only inside a task.
3. A critic that did not write the code reviews every PR, with one recorded exception: the fast lane (fixed decision below).
4. The check on the default branch is verified after every merge, with revert-once on red (v1 behaviour kept).
5. Existing `loop.local.json` files keep working: every new field is optional and defaults to v2 behaviour except where a task says otherwise.
6. Linked loop files change only by commit in `~/dev/agent-loop`.

## Budget

No paid vendor calls and no new runner spend. The cost is Claude Code usage, and v2.1 should lower it (fewer critic and merger agent runs). Any GitHub runner, plan or billing change (larger or sharded runners) is human-only and is not in this spec. A wave whose tokens exceed 2x the median of the last three waves is flagged in the scorecard (v2).

## Decision envelope

As v2: a recommendation is auto-accepted when it is reversible by one revert PR or one config edit, costs nothing or is under the project's cap (default 0), touches no invariant or fixed decision, and is not in a human-only category. Human-only categories: money or raising a cap; creating, rotating or sharing a secret; accounts, quotas, vendor plans (including repo settings such as enabling auto-merge); legal or privacy wording; irreversible production steps; changing a fixed decision or invariant.

## Fixed decisions

- **Bootstrapping.** As v2: this loop is built by the frozen checkout `~/dev/agent-loop-stable`, never by the copy it changes; the stable link moves to the new tag by a human step (H1).
- **Language and tests.** Node ESM, plain JavaScript with JSDoc, Vitest, Python 3 stdlib for the scorecard (`python3 -I`). Tests use no network and no real agent. Test files are `*.test.ts` under `tests/` or `claude/lib/`.
- **Modules.** The Workflow runtime accepts only self-contained scripts, so new logic is pure functions with injected I/O in `claude/lib/*.js`, bundled into workflow files by `scripts/bundle-workflows.js` between `@bundle-start` / `@bundle-end` markers. Bundled regions are never edited by hand.
- **CI is awaited by code, not by a model.** A function `waitForCi(prNumber, exec, opts)` polls `gh pr checks <n> --json name,state,bucket,link,workflow` every 20 s (bucket `pass` is green, `skipping` is ignored, `fail` and `cancel` are red, `pending` is pending; stdout is parsed whatever the exit code, because gh exits 8 while pending and 1 on failure; the log tail comes from `gh run view <id> --log-failed`, the run id parsed from `link`) until no check is pending or a timeout (default 20 min) passes, and returns `{ state: 'green'|'red'|'pending'|'missing', failing: [names], logTail }`. `missing` (no checks reported after 2 min) is not the worker's fault. No agent prompt tells a model to watch CI.
- **Pending CI is never a FIX.** The critic's job excludes CI. The workflow combines: verdict MERGE and CI `green` goes to merge; verdict MERGE and CI `red` becomes a FIX whose item is the failing check name and log tail (cause `defect`); `pending` after timeout becomes an escalation, not a FIX round; critic FIX or STOP stands whatever CI says, and a red CI appends its failing-check item to a critic FIX so one round fixes both; MERGE with CI `missing` escalates (never merges, never FIX). The critic starts at once, in parallel with the CI wait.
- **Merge is a script.** `scripts/merge-pr.js <pr> --repo <path> [--worktree <path>] [--dry-run]` replaces the merger agent. It reads the project config from `<path>/.claude/loop.local.json` (`syncPolicy`, `mainCi`, `install`, `check`, `checkMutates`) and prints one JSON line `{ outcome: 'merged'|'refused'|'reverted'|'error', exit, mergeSha, mainSha, ciState, failing, conflictFiles, revertPrUrl, message }` for the workflow to read. The caller holds the merge lock, so the script assumes it is the only merger on the repo. With `mainCi` empty it runs `install` then `check` once on the updated default branch through `.claude/slot.sh` (v1 behaviour) and restores the `checkMutates` files. `--dry-run` runs every read-only step and prints the calls it would make. Steps: read `mergeStateStatus` and sync main into the branch only as `syncPolicy` says (v1 meanings: `always` = when main has moved past the branch, read with `git merge-base --is-ancestor`; `conflict` = only when GitHub reports a conflict, `mergeable` CONFLICTING or `mergeStateStatus` DIRTY; `mergeable` UNKNOWN is re-read three times 10 s apart; the BEHIND value is never relied on) (v1 rule: merge main, no rebase, no force push); `waitForCi`; `gh pr merge <n> --merge --delete-branch`; wait for the `mainCi` run on the merge commit; on red, open one revert PR, wait for its CI with `waitForCi`, merge it only when green (invariant 1 has no revert exception), wait for the `mainCi` run on the revert merge, and exit with code 3 if main is green again or code 4 if the revert PR is not green in time or main is still red (no second revert). Exit codes: 0 merged and main green, 2 refused (CI not green or conflict), 3 reverted, 4 error. A sync conflict is never resolved by the script (the project's `syncConflicts` text is prose for a model): it aborts the merge, leaves the branch untouched, exits 2 with `conflictFiles`, and the workflow hands them to a worker fix round. `gh pr merge --delete-branch` can exit non-zero only because the local branch is checked out in a worktree: the script then confirms with `gh pr view --json state` and treats `MERGED` as success. After a merge it removes the task worktree and local branch when `--worktree` is given (step 6 of the v1 merger). Auto-merge is not used (repo setting is off; changing it is human-only). The existing merger agent stays selectable with `project.merger = 'agent'` for one release as the rollback.
- **Fast lane.** A task is fast-lane only if the spec marks it `Lane: fast` and a deterministic check agrees: every changed file is inside the task's `Owns`; no changed file is under a project `fastLane.denyPaths` list (default: workflow files, hookify rules, agent prompts, anything the spec names as an invariant); no forbidden string; CI green; test count not lower. A fast-lane task skips the critic and gets one FIX round at most. At most `fastLane.maxPerWave` (default 3) tasks per wave. Default is off (`fastLane.enabled: false`) until a human turns it on per project (H2).
- **Worker local checks.** The worker runs the typecheck, lint and tests of the files it changed (vitest `related` or the project's `quickCheck` command), not the full `check`; CI is the one full check. Projects without `quickCheck` keep the full local check.
- **Timings are measured, not guessed.** The scorecard's `--timings` view reports minutes per phase from the result JSON: build, local check, slot wait, review, CI wait, merge, main check, fix rounds, and the time the wave spent with zero agents running.
- **Spec review skip.** `spec-review` may be skipped for a wave of at most 3 tasks that are all `Lane: fast`; the human-only scan (secrets, accounts, money, legal, irreversible) still runs and a hit makes the review run in full.

## Wave 1: pure modules (1.1, 1.3 and 1.4 in parallel; 1.2 after 1.1)

- **1.1 CI wait.** Owns `claude/lib/ci.js`, `claude/lib/ci.test.ts`, `scripts/wait-ci.js`. `waitForCi(prNumber, exec, opts)` and `combineVerdict(criticVerdict, ci)` as defined in the fixed decisions, with injected `exec(command)` and `sleep`. A CLI `scripts/wait-ci.js <pr> [--repo <path>] [--timeout-min <n>]` wires real `gh` and `sleep`, runs the whole poll loop in one process and prints the result as one JSON line; the workflow reaches it through one relay agent that runs one command, never one agent call per poll. Reads or writes: reads (calls `gh pr checks` and `gh run view`; changes nothing). Test: a fake `exec` that returns recorded `gh` output with gh's real non-zero exit codes, for green, red (failing name and log tail returned), a `skipping` check ignored, a `cancel` check read as red, pending then green after three polls, pending until timeout, missing after 2 minutes; `combineVerdict(criticVerdict, ci)` takes the `waitForCi` result object and returns `{ action: 'merge'|'fix'|'escalate'|'stop', fixItems: [{ n, what, provedBy, cause }], reason }`; table: MERGE+green merges, MERGE+missing escalates, FIX+red keeps the critic's items and appends the failing check, MERGE+red is FIX with the failing check, MERGE+pending escalates and is never FIX, FIX+green stays FIX, STOP stays STOP.
- **1.2 Merge script.** Owns `scripts/merge-pr.js`, `claude/lib/merge.js`, `claude/lib/merge.test.ts`. Depends on 1.1. Implements the Merge-is-a-script decision with an injected `gh`/`git` runner. Reads or writes: writes-files (merges a pull request on the remote and, on red, opens a revert pull request; it never pushes to the default branch). Test: the merge logic against a fake runner whose `gh` outputs are recorded from real `gh` (fixtures `tests/fixtures/gh-*.json`: `pr view --json mergeStateStatus,mergeable,headRefOid` for a clean, a behind and a conflicting PR, `pr checks --json`, `run list`), plus one spawn test that runs `scripts/merge-pr.js` through a symlink in a temp repo with fake `gh` and `git` shims first on `PATH` and checks the exit code and the stdout JSON. Cases: merged and main green (exit 0); CI red (exit 2, no merge call made); `syncPolicy: always` with main moved merges main first; `conflict` with a clean but behind PR skips the sync; `conflict` with `mergeable: CONFLICTING` or DIRTY syncs; `mergeable: UNKNOWN` then MERGEABLE on the third read skips the sync; main red then revert PR opened, its CI awaited, merged and main green (exit 3); revert PR red, or main still red after the revert (exit 4, no second revert); `gh pr merge` refused (exit 2 with the message); `gh pr merge` exits 1 for the worktree branch but the PR state is MERGED (exit 0); a sync conflict (exit 2, conflict files listed, nothing pushed); `mainCi` empty runs the local check; no recorded call contains `--force`, `-f`, `--force-with-lease`, `--admin` or `--auto`; every `git push` names `origin` and the PR head branch or the revert branch, never the default branch; every recorded call is checked against the patterns in `claude/hookify.*.local.md`, because the script's own git calls do not pass through the hookify hooks; every `gh pr merge` carries `--match-head-commit <sha of the head that was green>`.

## Wave 2: wire it into wave-loop

- **2.1 Wave-loop uses code for CI and merge.** Owns `claude/workflows/wave-loop.js` (bundled regions via `scripts/bundle-workflows.js`, plus prompt text). Depends on 1.1, 1.2, 1.3. Critic prompt loses the CI instructions and the pending-means-FIX sentence; the critic runs in parallel with `waitForCi` and `combineVerdict` decides; on STOP the workflow does not wait for CI, and on FIX it waits for the CI result at most 5 minutes more before starting the fix round; `merger` agent calls are replaced by `scripts/merge-pr.js` (run as one command by the relay agent, labelled `merger:<id>`; the CI relay is labelled `ci:<id> r<n>`; each relay returns the command's stdout verbatim and its exit code and the workflow parses the JSON line in code, never trusting a relay-typed summary; the relay prompt allows `run_in_background` and says to wait for its completion notification, and a result with no parseable JSON line is retried once for wait-ci and never re-run for merge-pr.js, which escalates with the PR state because a second run on a merged PR reports 'refused'; the relay schema has `status` ran|blocked; before any worker starts, a preflight relay runs `merge-pr.js 0 --repo <repo> --dry-run` and a block or a missing script fails the wave with an escalation; a block during the wave sets `mergeBlocked`, parks the task, and later merge relays escalate without running; the relay runs no other command; `project.merger = 'agent'` stays available as the fallback) unless `project.merger = 'agent'` (which restores only the merger agent, with a prompt identical to v2's; the CI relay, `combineVerdict` and the new critic prompt stay on); fast-lane tasks skip the critic: `args.tasks[].lane` ('fast'|'normal', default normal) is set by the session from the task's `Lane:` line; for a `Lane: fast` task the critic is not started speculatively, one read-only relay gathers `changedFiles`, `addedText`, the PR body `Decisions:` lines and the `testCount` pair, `fastLaneEligible` decides after the CI result, an eligible task goes to the merge relay, an ineligible one gets the critic, and a fast task with red CI gets one FIX round; the per-wave counter is incremented synchronously when a task is found eligible;; escalation text names pending-CI timeout; the merge script's JSON line is stored in `tasks[id].merge` in the v1 shape (`outcome` merged|reverted|failed, `mergeSha`, `mainSha`, `checkOnMainExitCode`, `checkOnMainTail`, `revertPrUrl`, `details`) with the raw line under `script`, so the wave gate and the scorecard read it unchanged: exit 0 is merged; ## CI changes that belong in the pilot repo (short list for a later pilot spec, not loop tasks)

Measured: a `check` run is about 3.7 min; `npm ci` 34 to 41 s; vitest about 140 to 170 s (85% of `npm run check`); typecheck about 10 s and lint about 15 s.

1. Shard vitest 3 ways (matrix `--shard=i/3` with blob reporter, merge reports for the ratchet): about 3.7 min to about 2 min. Costs extra runner minutes (H3).
2. Cache `node_modules` keyed on lockfile hash and skip `npm ci` on a hit: about 30 s per job (setup-node `cache: npm` only caches the npm download cache).
3. `concurrency` with `cancel-in-progress: true` for `pull_request` runs only (never push to main): saves runner minutes and slot contention when a fix round pushes.
4. Docs-only PRs: do not use workflow-level `paths-ignore`, because `check` is required (skipped checks stay Pending and block the PR); use a path filter step inside the job.
5. Profile per-file vitest time from `.vitest-report.json` first; if pglite/tsx boot dominates, share one boot per worker before sharding.
6. Optional: split typecheck and lint into their own jobs for a fast red signal (about 1 min instead of 4); no wall-time gain for green runs.
7. Not recommended: caching `.tsbuildinfo` (under 5 s), `--changed` as the merge gate, self-hosted runner on the Mac, a merge queue, local status instead of CI.
