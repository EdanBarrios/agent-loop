# agent-loop v2: ordered task list (draft 1)

Date: 2026-10-30. Source: Edan's reflection after pilot waves 0 to 5 (`~/dev/pilot/CLAUDE.local.md`, "Edan's reflection and decisions"). Evidence of what hurt: `docs/pilot/HANDOFF.md`, `docs/pilot/2026-10-28-waves-3-5-questions.md`, the wave scorecards.

Execution model: as v1. Waves; tasks in a wave run in parallel; each wave ends with a tail task that runs alone. A wave is complete when the machine gate passes. A choice that falls inside the **decision envelope** below is made by the loop, not by a human.

## End goal

Edan is needed only for: money, secrets/accounts/quotas, legal wording, irreversible production steps, and fixed decisions. Everything else (spec review answers, wave launches, relaunches after a spec-defect escalation, scorecards, handoffs) the loop does itself and reports afterwards. A project spec can run from wave 0 to its last wave with one up-front human checklist and no mid-run questions that the envelope covers.

## Invariants (v1 rules stay)

1. Never commit to main, never force push (hookify rules stay; not weakened).
2. Deterministic control flow decides what runs next; models decide only inside a task.
3. A critic that did not write the code reviews every PR; verdicts MERGE, FIX, STOP.
4. Role models change one notch, one role per wave, only after a scorecard.
5. Existing `loop.local.json` files keep working: every new field is optional with a default that reproduces v1 behaviour, except where a task says otherwise.
6. Linked loop files change only by commit in `~/dev/agent-loop`.

## Budget

No paid vendor calls. The cost is Claude Code usage. Per wave, tokens are reported in the scorecard (task 1.5); no hard cap in v2, but a wave whose tokens exceed 2x the median of the last three waves of the same project is flagged in the scorecard. The critic falls back to `opus/high` when the Fable limit is hit (already possible through `project.models`; 4.1 makes it automatic).

## Decision envelope

A reviewer's or worker's recommendation is **auto-accepted** when all hold: reversible by one revert PR or one config edit; costs nothing or is under the project's cap (`project.envelope.maxCostCents`, default 0); touches no project invariant and no fixed decision; is not in a human-only category. **Human-only categories**: spending money or raising a cap; creating, rotating or sharing a secret; accounts, quotas and vendor plans; legal or privacy wording; irreversible production steps (schema migrations on a real database, sends, deletes, DNS); changing a fixed decision or invariant. Anything outside the envelope is put in the up-front checklist (if foreseeable) or an escalation (if not). Every auto-accepted decision is logged with its reason, and a decision later reversed counts in the **reversal rate** (scorecard).

## Fixed decisions

- **Bootstrapping.** agent-loop is built by its own loop, but never by the copy it is changing. A frozen checkout of the last released tag lives at `~/dev/agent-loop-stable` (a git worktree of tag `v1`), and `install.sh` links `.claude/` in `~/dev/agent-loop` to that checkout. A new tag is cut and the link moved only by a human step after the wave gate (checklist item H3).
- **Language and tests.** Node ESM, plain JavaScript with JSDoc (the workflow script runs without a build step), Vitest. Python 3 stdlib only for `scripts/loop-scorecard.py`, run with `python3 -I`. The existing `tests/wave-loop.test.ts` harness (stubbed `agent()`) is the model for workflow tests; tests use no network and no real agent.
- **Test files** are TypeScript, named `*.test.ts`, and live under `tests/` or `claude/lib/`; those are the only globs the vitest config finds (wave 0, `vitest.config.ts`), so a test elsewhere never runs. Modules under test may stay `.js`.
- **One check.** `npm run check` runs: `node --check` on every file under `claude/`, `python3 -I -m py_compile scripts/*.py`, `vitest run`. CI runs the same.
- **Modules.** The Workflow runtime accepts only self-contained scripts: `import()` and static `import` are both rejected (found by probe on 2026-10-31; wave 2's `spec-review.js` used `await import` and cannot launch as merged). So new logic is written as pure functions with injected I/O in `claude/lib/*.js` (tested as ESM), and a bundler (`scripts/bundle-workflows.js`, 3.1) copies each lib's source, with `export` keywords removed, into the workflow files between `// @bundle-start <lib>` and `// @bundle-end <lib>` marker lines. The bundled regions are generated: never edited by hand, and `node scripts/bundle-workflows.js --check` (part of `npm run check`) fails when a region differs from its lib. `claude/lib` is not linked into `.claude/`. Scripts have no filesystem, clock or shell: file writes and shell commands go through a small agent.
- **Config.** New optional `loop.local.json` fields: `envelope` (`{ maxCostCents, humanOnly: [extra category strings] }`), `gates` (path to the gate checklist, default `docs/gates.json`), `realityCheck` (`{ command, readOnly: true, timeoutSec }`), `chain` (`{ after: '1', minFirstPassRate: 0.7, stopOn: ['gate_fail','escalation','reality_gap'] }`; this object is the default, so a project with no `chain` field chains after wave 1; `chain: false` turns it off). Reading the wave 1 PRs is the learning gate; once wave 1's first-pass merge rate is at least `minFirstPassRate`, later waves chain and park only on an escalation. Unknown fields are ignored.
- **Gate checklist** (`gates.json`): array of `{ id, what, why, owner: 'human', before: <wave id>, leadTime: 'minutes'|'hours'|'days', status: 'open'|'done'|'waived', evidence }`; items with `leadTime: 'days'` are listed first, because they are the ones that stall a wave (pilot's Vertex quota took a day and surfaced at wave 4). The loop refuses to start wave N while any item with `before <= N` is `open`, and says which.
- **Reality check** contract: the command prints one JSON object `{ gaps: [{ id, severity: 'block'|'warn', what }] }` and exits 0. It must be read-only; the spec's task for it carries a `Reads or writes:` line and the lint (1.4) rejects `writes`. A `block` gap fails the gate.
- **Command specs** (any task that adds a CLI command or script a human or the schedule will run) state `Reads or writes:` as one of `reads`, `writes-db`, `writes-files`, `paid-call`, `sends`. `paid-call` and `sends` require the human-only review before the wave runs.
- **Spec review is one round**: reviewer, spikes, adversarial reviewer, envelope, build. A second recommendation round only if the adversarial reviewer returns a `block` finding.
- **Route by verifiability.** A role may run on a cheaper model only when its output is checked mechanically afterwards (CI, the check on the default branch, a recorded source). Judgment roles (critic, adversarial reviewer, tiebreaks) stay on the strongest model. Same-family agreement is not independent evidence: anything load-bearing needs deterministic ground truth (a test, a fixture, a fetched source) or a different-family reviewer, not another Claude agreeing. Models are pinned by full id, never alias, so the scorecard baseline cannot drift; the scorecard flags any run whose served model differs from the requested one.
- **Chaining is the default**: wave 1 of a project is human-read. After it, the loop runs the next wave automatically when the first-pass rate holds and the machine gate is PASS, the reality check has no `block` gap, no escalation is open, and the next wave has no open gate item.

## Risk-class obligations

- Changing `wave-loop.js` is the highest-risk change: every wave of every project runs it. Wave 3 does not edit it (chaining lives in `chain-loop.js`); each later task touching it states its v1-behaviour regression test (4.1 no-config case, 4.2 prompt snapshots). The stable-checkout rule is the safety net.
- Auto-accept must not hide a human-only decision: 1.1's `touches: fixed_decision` and category tests, and the 2.T regression on the Apollo money question.
- The reality check is the only place the loop touches a real system; read-only is enforced by config (`readOnly: true` required, 1.3) and by lint (1.4), not by trusting the command.

## Model trials (runs, not tasks)

One role per wave, one notch, per the README. Wave 1 runs with `project.models.merger = { model: 'claude-haiku-5-5', effort: 'low' }` and compares to the wave 0 scorecard: merger failures or reverts must stay at zero and the merger's share of tokens should fall. A failed merge reverts the role to Sonnet/low next wave. The worker stays Sonnet/high. The next trial (wave 2) is the worker on Haiku/high for tasks whose acceptance test is a pure table test (1.1-style), only if the wave 1 merger trial is clean.

## Failure handling and envelope growth

- A decision that fails twice (its fix round also fails, or it is reversed once and the replacement fails) escalates; the loop never runs a third recommendation round on the same item. Task 4.2 puts this in the worker and escalation rules; 1.1's `ledger` counts `failures` per decision id.
- The envelope widens one notch at a time, one dimension per project per wave, and only after a scorecard shows a reversal rate under 10% over at least 20 decisions. Task 1.5 prints that verdict; moving the envelope is a human step.

## Out of scope for v2

Multi-project shared budgets and cross-project scorecards; a scheduler that wakes the loop on a timer (chaining runs inside one Workflow call); automatic tag cutting and stable-link moves; changing default models; any change to the hookify rules; pilot v2 (templates and reply handling), which is its own spec and runs after this one.
